# 规约驱动开发（SDD）说明书

> 这份文件回答一个问题：**在这个项目里，我怎样把「想要什么」写成大模型能照着做的规格，并且能验收。**

---

## 1. 为什么用 SDD

这个项目大部分代码是大模型写的。如果只丢一句「帮我写个背单词 App」，会得到三个后果：

1. 需求落不了地——模型不知道「考研英语一难度」具体指多少词的句子；
2. 无法验收——没人说得清「做完了」是什么样；
3. 改动会互相打架——同一个「单词」概念，页面、接口、数据库各写一遍。

SDD 的做法是把「要求」先固化成可检查的文本，再让模型在文本约束下产出代码：

```
需求（人话）
  → 规约（可验收的规格 + 数据结构 + 接口契约）
  → 评测集（每个规约条目对应一条或多条检查）
  → 模型实现
  → 跑测试 / 人工验收（不过就回到规约补充）
```

本项目对应的四份材料：

| 材料 | 文件 | 作用 |
|---|---|---|
| 需求 | `REQUIREMENTS.md` | 业务上要做什么、优先级、边界 |
| 规约 | 本文件 + `docs/api.md` + `docs/er.md` | 每个功能的输入输出、数据结构、约束 |
| 评测集 | `docs/sdd/eval-set.md` | 规约条目 → 可执行的检查项 |
| 验收 | `docs/sdd/acceptance.md` | 里程碑达成情况与证据 |

## 2. 规约怎么写（本项目实际采用的模板）

每条需求都按同一张表写，写不出来就说明需求还没想清楚：

| 字段 | 说明 | 反例 | 正例 |
|---|---|---|---|
| 编号 | 稳定标识，测试注释里引用 | — | `OCR-03` |
| 输入 | 用户给什么，格式、大小上限 | 「一张图」 | 「PNG/JPG，≤10 MB，单词卡截图」 |
| 处理 | 走哪条链路、失败怎么降级 | 「识别一下」 | 「百度 OCR → 失败降级 Tesseract → 再失败 mock；结果进候选区不入库」 |
| 输出 | 用户看到什么 | 「显示单词」 | 「候选词卡片列表，可逐条编辑/删除，点保存才入库」 |
| 约束 | 性能、耗时、费用、权限 | 「要快」 | 「同一张图第二次调用命中缓存，≤100 ms；单次识别≤5 s」 |
| 验收 | 怎么证明做到了 | 「能用就行」 | 「`eval-set.md` 中 `OCR-03` 三条检查全部通过」 |

### 2.1 一个完整例子（OCR-03 人工校正）

```text
编号：OCR-03
输入：候选词列表（来自 OCR 或粘贴），用户可编辑
处理：
  1. 每张图识别完成后进入候选区，不直接写库；
  2. 用户可改拼写、可删单条、可清空；
  3. 点「保存这些词」才 POST /api/words；
  4. 重复词走 upsert，不产生重复行。
约束：候选区最多展示 60 条；保存失败要给出可读原因（不是异常类名）。
验收：见 eval-set.md OCR-03。
```

## 3. 规约如何约束模型产出

给模型的提示词里固定带三样东西，避免「自由发挥」：

1. **数据结构**：直接贴 `docs/er.md` 里的表定义与被改动的字段；
2. **接口契约**：贴 `docs/api.md` 里对应接口的请求/响应示例；
3. **不许动的地方**：例如「不要改 `ApiResponse` 的字段名」「不要把 Key 写进代码」。

例：让模型实现「补全词典查不到的词」时，提示词里明确要求：

- 只输出 `[{"word","phonetic","pos","cn"}]`，不许多字段；
- 词典里已有的词不调用模型（不花钱）；
- 结果写 `lookup_cache`，`source="model"`；
- 单次最多 40 个词。

模型产出的代码就是按这张单子逐条对应的。

---

## 4. 三条硬约束（写进所有提示词的「护栏」）

| 护栏 | 内容 | 为什么 |
|---|---|---|
| 不碰密钥 | API Key 只从配置/数据库读，不写死在代码里，不进 Git | 仓库是公开的 |
| 不破契约 | 接口路径、返回结构、表名一旦定了，改动必须同步 `api.md` / `er.md` | 前后端分离后靠契约对齐 |
| 不越权 | 所有查询带 `user_id`，A 用户的数据 B 用户看不到 | 多用户系统的底线 |

违反任一条，代码评审直接打回——本项目三轮评审里被退回的问题，一半属于这三类。

---

## 5. 人工审批点（高风险动作必须人点头）

| 动作 | 为什么高风险 | 审批方式 |
|---|---|---|
| 改数据库结构（建表/加列/加外键） | 影响存量数据 | 先给 `ALTER` 语句，人工在库上执行 |
| 调用付费接口（DeepSeek / 百度 OCR） | 直接花钱 | 生成文章、补释义、AI 查词都要用户点击触发 |
| 删除数据（清空单词/生词/文章） | 不可恢复 | 前端二次确认 + 后端只接受显式 `DELETE` |
| 打包发布 | 影响可运行状态 | 先跑 54 个单测 + 手工点三条主链路 |

## 6. 迭代记录（三轮评审共 24 个问题）

| 轮次 | 主要问题 | 处理 |
|---|---|---|
| 第 1 轮（10 条） | mock 冒充当真实识别、降级无提示、生成无事务、无单测、文档与实现不符 | 引入 `OcrResolver` 链式降级、`ArticleStore` 事务、`ArticleValidator`、异常处理器、5+4 个单测 |
| 第 2 轮（8 条） | `@ConditionalOnProperty` 导致 auto 只剩 mock、`bindPending()` 从未调用、多图绕过候选词 | 去掉条件注解改为构造注入、补调用、多图统一走候选区，测试加到 13 个 |
| 第 3 轮（6 条） | mock 结果被缓存、`provider: mock` 不生效、历史 N+1、搜索只覆盖一栏 | 缓存前判 mock、链路加 mock 分支、批量查询、三栏统一搜索排序，测试加到 23 个 |

每一轮都按「问题 → 归属规约条目 → 改代码 → 补评测项」走，没有出现「改 A 坏 B」。

## 7. 这套做法的收益与代价

**收益**

- 需求变更时改的是文本，不是散落在代码里的隐式约定；
- 模型产出可校验：54 个单测里，大部分直接对应 `eval-set.md` 的条目；
- 换人接手成本低：`api.md` + `er.md` + 本文件基本能还原设计意图。

**代价**

- 前期写规约的时间不比写代码少；
- 规约写得不够具体时，模型会「合理猜测」，反而更难查；
- 需要纪律：代码改了不同步文档，下一次模型就会照着过期文档写。

---

## 8. 结论

SDD 在本项目里起作用的不是「流程」，而是**把模糊需求变成可执行断言**。
只要每条需求都能写成「输入—处理—输出—约束—验收」五段，大模型产出的代码就能被检验；
写不出来的条目，基本也都是我自己还没想清楚的地方。
